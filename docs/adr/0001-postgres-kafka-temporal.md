# 0001. Postgres — источник истины, Temporal — процесс, Kafka — трансляция

Статус: принято.

## Контекст

В системе три технологии, каждая из которых умеет «хранить состояние»: Postgres,
Kafka и Temporal. Если не провести границу заранее, состояние расползётся по всем
трём, и на вопрос «какой сейчас статус у заказа» появится три разных ответа.

Жизненный цикл заказа при этом не помещается в один HTTP-запрос: между оформлением
и доставкой есть семиминутный таймер подтверждения, сигналы от заведения, отмена
пользователем и компенсации, если что-то пошло не так. И одновременно есть
наблюдатели — витрина поиска, уведомления, статистика, — которым нужны факты
о заказе, но не нужен его процесс.

## Решение

Роли разведены жёстко:

- **Postgres — источник истины.** Все чтения идут в него. `orders.status` —
  проекция состояния процесса; пишут её только activities, читает HTTP API.
- **Temporal — процесс одного заказа.** Durable-таймеры, сигналы, компенсации.
  Workflow не имеет своего хранилища состояния для внешнего мира: то, что должно
  быть видно снаружи, он кладёт в Postgres через activity.
- **Kafka — трансляция фактов наблюдателям.** Односторонняя: из системы наружу.
  Ни один запрос пользователя не ждёт Kafka, и ни одно решение не принимается
  по её содержимому.

Практическое следствие: доставка заказа в POS — это activity Temporal, а не
Kafka-консьюмер, потому что процессу нужен **результат** вызова, чтобы решать,
что делать дальше. Наблюдателям результат не нужен — они на Kafka.

## Последствия

- Отладка предсказуема: «где правда» — вопрос без вариантов, ответ всегда Postgres.
- Падение worker'а не роняет выдачу каталога: заказы копятся в outbox, API отвечает.
- Плата — три инфраструктурные зависимости в compose вместо одной. Для MVP это
  дорого, и я считаю это оправданным только потому, что сценарии задания
  (таймер подтверждения, компенсации, отказ POS) — ровно те, ради которых
  оркестратор и заводят.
- Temporal становится единственной точкой, где живёт «время» бизнес-процесса.
  Тесты workflow проходят durable-таймеры за миллисекунды, поэтому семиминутный
  таймер проверяется юнит-тестом, а не ожиданием.

## Отвергнутые альтернативы

**Cron + таблица задач.** Пришлось бы своими руками написать то, что Temporal даёт
из коробки: идемпотентность шагов, повторы с backoff, историю выполнения,
компенсации. Это не «проще», это «то же самое, но без истории и без тестируемости».

**Только Kafka, без Temporal.** Kafka не умеет «разбудить меня через семь минут
и дать отменить пробуждение сигналом». Эмуляция через отложенные топики —
самодельный планировщик поверх лога.

**Только Temporal, без Kafka.** Каждый новый наблюдатель (поиск, уведомления,
статистика) пришлось бы вписывать в workflow заказа. Workflow стал бы знать
про витрину поиска — связанность, которой в нём быть не должно.

**Состояние заказа внутри workflow, без проекции в Postgres.** Тогда `GET /orders`
ходил бы в Temporal через query. Это медленно, это делает историю заказов
недоступной при недоступности Temporal, и это лишает возможности написать
обычный SQL-отчёт.
