# 0006. Диаграммы — Mermaid инлайном в markdown

Статус: принято.

## Контекст

Задание требует CJM «в формате code-generated диаграмм (PlantUML или аналог)»
и C4-диаграмму в README. Диаграмм в проекте много: два CJM, три уровня C4, три
ERD, машина состояний, три sequence-диаграммы. Их будет читать проверяющий,
открыв репозиторий на GitHub.

## Решение

Mermaid, инлайном в markdown-файлах. Отдельного шага сборки нет, картинки
не коммитятся.

## Последствия

- GitHub рендерит Mermaid прямо в превью: диаграммы видно, не клонируя репозиторий
  и не поднимая Java-тулчейн.
- Источник диаграммы лежит рядом с текстом, который её объясняет, и правится
  в том же коммите. Расхождение «текст обновили, картинку забыли» становится
  заметным на ревью.
- У Mermaid есть тип `journey` — буквально Customer Journey Map, а также
  `erDiagram`, `stateDiagram-v2` и `sequenceDiagram` для остального. Отдельный
  формат ни для одной диаграммы не понадобился.
- Плата — Mermaid беднее PlantUML в раскладке: нет C4-примитивов (`Container`,
  `Rel`), поэтому C4 нарисован `flowchart`'ом с ручными стилями. Уровни и легенду
  приходится держать соглашением, а не синтаксисом.
- Синтаксическая ошибка на GitHub выглядит как пустой блок, а не как ошибка,
  поэтому диаграммы прогоняются через `mermaid-cli` перед коммитом — глазами
  такое не ловится.

## Отвергнутые альтернативы

**PlantUML.** Богаче, есть готовый `C4-PlantUML` со стандартными примитивами.
Но GitHub его не рендерит: нужен либо коммит картинок (расходятся с исходником),
либо внешний сервер рендеринга (ссылка протухнет), либо локальный Java-тулчейн
у читателя. Любой из трёх вариантов ухудшает то, ради чего диаграммы и рисуют, —
чтобы их посмотрели.

**Structurizr DSL.** Правильный инструмент именно для C4 с одной моделью на все
уровни. Но это отдельный рендерер и отдельный артефакт сборки ради трёх диаграмм.

**Картинки из редактора (Excalidraw, draw.io).** Не code-generated — прямо
противоречит критерию приёмки, и не дают diff'а в ревью.
