# 0004. Перечисления — `text` + `CHECK`, а не Postgres `ENUM`

Статус: принято.

## Контекст

В схеме есть перечисления: статус заказа (девять значений), статус заведения,
тип актора перехода, статус платежа, тип агрегата в outbox. Часть из них ещё
будет меняться — статус заказа за время реализации получил `payment_failed`
и `expired`.

## Решение

`text` со `CHECK (col IN (...))`. Postgres `ENUM` не используется.

## Последствия

- Добавить значение — обычная миграция, которая меняет `CHECK`. Убрать значение —
  тоже обычная миграция.
- Значения читаемы в дампе и в `psql` без join'ов и без справочника типов.
- В Go статусы — строковые константы с типом-обёрткой (`order.Status`), а линтер
  `exhaustive` следит, чтобы новый статус не забыли обработать в `switch`.
  Проверка исчерпаемости переезжает в компилятор и линтер — туда, где ей место.
- Плата — `text` занимает больше, чем 4-байтовый `oid` `ENUM`'а, и не даёт
  сортировки в порядке объявления. На объёмах MVP незаметно; порядок статусов
  всё равно задаётся матрицей переходов, а не сортировкой.
- `CHECK` не мешает `ALTER TABLE` и не блокирует таблицу надолго при изменении
  (в отличие от `ALTER TYPE ... ADD VALUE`, который до PG12 нельзя было
  выполнять в транзакции).

## Отвергнутые альтернативы

**Postgres `ENUM`.** Значение из него **нельзя удалить** — только пересоздавать
тип со всеми зависимостями. Для перечисления, которое ещё меняется, это ловушка.

**Справочная таблица с FK.** Даёт целостность и человекочитаемое описание,
но за каждое чтение статуса платим join'ом, а за каждое новое значение — строкой
данных в миграции. Для замкнутых наборов из десятка значений, которые всё равно
захардкожены в коде, это лишний слой.

**Без ограничения вовсе.** Тогда опечатка в коде тихо ложится в базу и всплывает
через месяц как заказ в статусе `acepted`.
